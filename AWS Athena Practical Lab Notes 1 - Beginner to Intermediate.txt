📄 Source File: employee.csv

📋 Data 
🔺 id,fname,lname,age
🔺 1,Sham1,G,30
🔺 2,Sham2,G,30
🔺 3,Sham3,G,26
🔺 4,Sham4,G,26

📤 Uploaded to: s3://chennai-dba-community/athena-lab/csv/


1) 🔴 Create CSV Athena Table
===============================
➔ SQL❯ create external table EMPLOYEE_CSV 
(  
	id INT, 
	fname STRING, 
	lname STRING, 
	age INT 
) 
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE 
LOCATION 's3://chennai-dba-community/athena-lab/csv/' 
TBLPROPERTIES ('skip.header.line.count'='1');

✅ Validation : SELECT * FROM employee_csv;
📊 Result     : Successfully returned 5 records.

📘 Purpose : TBLPROPERTIES - skip.header.line.count'='1
=======================================================
🔸 ('skip.header.line.count'='1') 
🔸 Instructs Athena to skip the first row of the CSV file.
🔸 Prevents the Header Row from being treated as actual data.
🔸 Example -> id,fname,lname,age
🔸 Without skip.header.line.count='1', Athena may attempt to read the header as a data record.

💡 Learning
🔸 CSV files already existed in S3.
🔸 Athena only created metadata.
🔸 Athena did not move or copy any data.

💡 Additional Learning
🔸 CSV files are not Self-describing.
🔸 CSV files do not store schema metadata, column definitions, or data types internally.
🔸 Athena maps CSV columns based on position.
🔸 If column order changes in the file, Athena may return incorrect results.
🔸 Athena depends entirely on the table definition for column names and data types.

🟢 Lab 6 - First Attempt at Parquet File (Failed) 🚨
-----------------------------------------------------
🔶 Objective
🔸 Validate Athena support for Parquet files.

🔶 Initial Attempt
🔸 Created: employee.parquet using Notepad++ and uploaded it to S3.

🔶 Created Athena table: 
🔸CREATE EXTERNAL TABLE employee_parquet_file (...)

✅ Validation:
✅ SELECT * FROM employee_parquet_file;

🚫 Error Encountered:
🔸 HIVE_BAD_DATA: Malformed Parquet file
🔸 Expected magic number: PAR1

🔎 PAR1  Verification
🔸 File Name: employee.parquet
🔸 File Size: 95 bytes


🔍 Root Cause Analysis
------------------------
🔸 Although the file extension was: .parquet the file content was plain text.
🔸 Athena expected a genuine Parquet binary file.

💡 Learning
🔸 Changing a file extension does not change the underlying file format.

Example: 
employee.csv
⬇️
Rename to employee.parquet
⬇️
Still NOT a valid Parquet file

🔸 Simply renaming a CSV or text file with a .parquet extension does not convert it into a Parquet file.
🔸 Athena validates the actual file structure and binary format, not just the file extension.

💡 Understanding PAR1 Signature:
🔸 PAR1 is a special signature used by Parquet files.
🔸 Athena checks for the PAR1 magic number while reading Parquet files.

👉 If PAR1 is not found, Athena treats the file as invalid and throws errors such as:
🚫 HIVE_BAD_DATA: Malformed Parquet file
🚫 Expected magic number: PAR1


🧹 Cleanup Activities:
----------------------
🔸️ Deleted: employee.parquet from S3.
🔸️ Dropped Athena table:
🔸 DROP TABLE employee_parquet_file;
🔸 Started the validation again using a genuine Parquet file.

💡 Additional Learning
🔸 DROP TABLE employee_parquet_file;
🔸 It removes only Athena / Glue Catalog metadata.
🔸 DROP TABLE does NOT delete files stored in Amazon S3.
🔸 Deleting employee.parquet from S3 was a separate manual activity.

Flow:

DROP TABLE
⬇️
Athena Metadata Removed
⬇️
S3 File Still Exists
⬇️
Manual S3 Deletion Required


🟢 Lab 7 - Generate a Valid Parquet File Using Python
-------------------------------------------------------

📘 Purpose

📝 Create Python Script
--------------------------
📄 File Name: create_parquet.py
🔸 The Python script creates employee data using a Pandas DataFrame.
🔸 The DataFrame is converted into a Parquet file using PyArrow.

⚠️ Important:
🔸 At this stage only the Python script exists.
🔸 Parquet file is created only after script execution.

➜ Execute Script
🔸 Open Command Prompt.
🔸 Navigate to the folder where: create_parquet.py is stored.
🔸 Example: cd Desktop\AWS_DE
🔸 Execute: python create_parquet.py

📋 Output:
🔸 employee_new.parquet created successfully
🔸 File Size: 2709 bytes

Python Script Code:
---------------------
import pandas as pd
import os

df = pd.DataFrame({
    'id':[1,2,3,4,5],
    'fname':['Sham1','Sham2','Sham3','Sham4','Sham5'],
    'lname':['G','G','G','G','G'],
    'age':[30,30,26,26,26]
})

file_path = 'employee_new.parquet'

df.to_parquet(file_path, index=False)

print("employee_new.parquet created successfully")
print("File Size:", os.path.getsize(file_path), "bytes")

💡 Learning
🔸 The Parquet file is physically created only when the script is executed.
🔸 Creating a Python script does not create a Parquet file. The Parquet file is generated during execution of df.to_parquet().
🔸 Pandas prepares the data, while PyArrow performs the actual Parquet file generation.

🔄 What Happened Internally ?
------------------------------
Python Script
⬇️
Pandas DataFrame
⬇️
PyArrow Engine
⬇️
Parquet Conversion
⬇️
employee_new.parquet
⬇️
Valid Parquet File Created.  


✅ Verification: 
🔹 Invalid File: employee.parquet
🔹 Size: 95 bytes
📋 Result: Athena Failed

🔹 Valid File: employee_new.parquet
🔹 Size: 2709 bytes
📋 Result: Valid Parquet File Generated Successfully


🟢 Lab 8 - Upload Valid Parquet File and Query Using Athena
---------------------------------------------------------
📌 Purpose: Validate that Athena can successfully read and query a genuine Parquet file stored in Amazon S3.
📤 Uploaded: employee_new.parquet to: s3://chennai-dba-community/athena-lab/parquet/


3)🔴 Create Athena Parquet Table:
===================================
➔ SQL❯ CREATE EXTERNAL TABLE employee_parquet_file 
( 
  id INT, 
  fname STRING, 
  lname STRING, 
  age INT 
) 
STORED AS PARQUET 
LOCATION 's3://chennai-dba-community/athena-lab/parquet/';

✅ Validation
✅ SELECT * FROM employee_parquet_file;
📋 Result : All 5 rows successfully returned.

💡 Learning
🔸 This approach is used when the Parquet file already exists in S3.
🔸 Athena only creates metadata.
🔸 Parquet is a self-describing file format.
🔸 Column names, data types, metadata, and compression information are stored inside the Parquet file.
🔸 Unlike CSV, Athena can validate the embedded schema stored in the Parquet file.
🔸 LOCATION points to a folder and not an individual file.
🔸 Athena scans all compatible files available inside the specified folder.
🔸 Any new compatible file added to the folder may automatically become part of query results.
🔸 Parquet files are not Human-Readable because they are stored in a binary columnar format.
🔸 Parquet files can be viewed using tools such as Athena, Pandas, PySpark, AWS Glue, Microsoft Fabric, or Parquet viewers.


🔴 Additional Experiment - Pandas index=False vs index=True
============================================================
📌 Purpose: Understand the impact of storing the DataFrame index inside a Parquet file and observe its effect on file size and Athena query results.

👉 Test 1:
df.to_parquet(file_path, index=False)

👉 Test 2:  
df.to_parquet(file_path, index=True)

📌 Observation:
🔸 index=False generated a Parquet file of 2709 bytes.
🔸 index=True generated a Parquet file of 3645 bytes.
🔸 File size increased because the DataFrame index was stored in the Parquet file.
🔸 No additional column appeared in Athena query results even when index=True was used.
🔸 Athena query output remained unchanged.
🔸 The additional Pandas index information remained stored inside the Parquet file but was not exposed through the Athena table definition.

💡 Learning 
🔸 index=False creates a smaller Parquet file.
🔸 index=True creates a larger Parquet file by storing the DataFrame index.
🔸 Athena query results remained identical in both cases.
🔸 For Athena workloads, index=False is generally preferred because it produces smaller files without affecting query results.


🟢 Lab 9 - CSV to Parquet Conversion Using CTAS
------------------------------------------------
🎯 Objective: Convert CSV data into Parquet format using Athena itself.

📘 CTAS Without EXTERNAL Location
==================================
➔ SQL❯ create table EMPLOYEE_PARQUET_TAB1 
WITH (format='PARQUET')
AS SELECT * FROM employee_csv;

➔ SQL❯ create table EMPLOYEE_PARQUET_TAB2
WITH (format='PARQUET')
AS SELECT * FROM employee_csv;

✅ Validation:
✅ SELECT * FROM EMPLOYEE_PARQUET_TAB1;
✅ SELECT * FROM EMPLOYEE_PARQUET_TAB2;

📋 Result:
🔸 All 5 rows returned successfully.
🔸 Both succeeded with NO CONFLICT.
🔸 When external_location is not specified, Athena automatically manages a unique storage location for each CTAS table.
🔸 Athena handles storage path uniqueness automatically.  


📘 CTAS with EXTERNAL LOCATION ➔ Unique Folder is required.
=============================================================
➔ SQL❯ create table EMP_PARQUET_CTAS1 
WITH (format='PARQUET', 
	  external_location='s3://chennai-dba-community/athena-lab/parquet_ctas1/' ) 
AS SELECT * FROM employee_csv;


➔ SQL❯ create table EMP_PARQUET_CTAS2
WITH (format='PARQUET', 
	  external_location='s3://chennai-dba-community/athena-lab/parquet_ctas2/' ) 
AS SELECT * FROM employee_csv;

✅ Validation:
✅ SELECT * FROM EMP_PARQUET_CTAS1;
✅ SELECT * FROM EMP_PARQUET_CTAS2;
📋 Result -> All 5 rows returned successfully.

📌 Empty Target Folder Requirement
🔸 CTAS generates new output files.
🔸 The target folder should be empty before execution.
🔸 If the target location already contains files : 🚫 HIVE_PATH_ALREADY_EXISTS

💡 Learning
🔸 CTAS writes data.
🔸 CREATE EXTERNAL TABLE reads data.

💡 Additional Learning
🔸 Table Name Uniqueness and S3 Location Uniqueness are different concepts.
🔸 Different table names can still fail if they attempt to write to the same S3 location.
🔸 Each CTAS operation should use a unique empty folder when external_location is specified.
🔸 Reusing a non-empty location can result in HIVE_PATH_ALREADY_EXISTS errors.
🔸 Athena prevents CTAS operations from overwriting existing files in the target location.

📘  CREATE EXTERNAL TABLE vs CREATE TABLE AS SELECT (CTAS):
===========================================================
📌 Purpose: Understand when Athena should read existing files versus when Athena should generate new output files.

CREATE EXTERNAL TABLE:
----------------------
Used when data already exists in Amazon S3 and Athena only needs metadata to access the data.

Example Use Cases:
🔸 CSV file already uploaded to S3
🔸 JSON file already uploaded to S3
🔸 Parquet file already uploaded to S3
🔸 ORC or Avro file already uploaded to S3

🔄 How It Works:
----------------
Existing Data Files in Amazon S3
⬇️
CREATE EXTERNAL TABLE
⬇️
Metadata Created in AWS Glue Catalog
⬇️
Athena Reads Data Directly from Amazon S3
⬇️
Query Results Returned

Key Points:
🔸 Athena does not create or modify any data files.
🔸 Only table metadata is created.
🔸 Data remains in S3.
🔸 Athena expects data files to exist in the specified S3 location.
🔸 Commonly used for CSV, JSON, Parquet, ORC, and Avro files.
🔸 Table creation succeeds even if the S3 location contains no files.
🔸 Queries will simply return zero rows until data is available.


📌 Purpose of CTAS (CREATE TABLE AS SELECT):
--------------------------------------------
🔸 Used when Athena needs to generate new output files and create a new table.
🔸 The data written by CTAS is the result set produced by the SELECT statement.

Example Use Cases:
🔸 CSV  → Parquet conversion
🔸 JSON → Parquet conversion
🔸 Data filtering
🔸 Data aggregation
🔸 Data optimization
🔸 Creating analytics-ready datasets

🔄 How It Works:
------------------
Source Data Files in Amazon S3
⬇️
Athena Reads Source Data from Amazon S3
⬇️
Athena Generates New Output Files
⬇️
New Files Stored in Amazon S3
⬇️
Metadata Created in AWS Glue Catalog
⬇️
New Table Available for Querying

Key Points:
🔸 Athena creates new output files in S3.
🔸 Athena creates metadata for the new table.
🔸 Useful for format conversion and performance optimization.
🔸 Target location should be empty before execution.
🔸 May fail with HIVE_PATH_ALREADY_EXISTS if files already exist in the target location.

🟡 CREATE EXTERNAL TABLE Vs CTAS - CREATE TABLE AS SELECT
==============================================================================================
Feature                         | CREATE EXTERNAL TABLE       | CTAS (CREATE TABLE AS SELECT)
--------------------------------|-----------------------------|-------------------------------
Purpose                         | Read existing data          | Generate new data
Data files already exist in S3  | Yes                         | Yes (Source Data)
Creates metadata                | Yes                         | Yes
Creates new data files          | No                          | Yes
Reads data from S3              | Yes                         | Yes
Writes data to S3               | No                          | Yes
Uses LOCATION                   | Yes                         | No
Uses EXTERNAL_LOCATION          | No                          | Yes
CSV  -> Parquet Conversion      | No                          | Yes
JSON -> Parquet Conversion      | No                          | Yes
Requires empty target folder    | No                          | Yes
--------------------------------|-----------------------------|-----------------------------------------
Typical Use Case                | Register existing files     | Create transformed/optimized  datasets 
=========================================================================================================


📘 LOCATION vs EXTERNAL_LOCATION
==================================
📌 Used With:
CREATE EXTERNAL TABLE

📌 Purpose: Identify the Amazon S3 folder that already contains data files.
SQL❯ CREATE EXTERNAL TABLE <table_name> 
    (...} 
    LOCATION 's3://chennai-dba-community/athena-lab/csv/';

🔄 How It Works:
-----------------
Existing Files in Amazon S3
⬇️
LOCATION
⬇️
Metadata Created in AWS Glue Catalog
⬇️
Athena Reads Existing Files from Amazon S3
⬇️
Query Results Returned

📌 Key Points:
---------------
🔸 LOCATION points to an existing S3 folder.
🔸 Data files must already be present in the specified location.
🔸 Athena does not create or modify any data files.
🔸 Empty folders do not cause errors, but queries return zero rows.
🔸 Multiple tables can point to the same S3 location.
🔸 LOCATION is a read-only reference to the folder containing existing data files.

📌 Used With:
CREATE TABLE AS SELECT (CTAS)

📌 Purpose: Specify the Amazon S3 folder where Athena should create new output files.

SQL❯ CREATE TABLE <table_name>
    WITH (...)
    EXTERNAL_LOCATION='s3://chennai-dba-community/athena-lab/parquet_ctas1/'
AS SELECT * FROM employee_csv;


🔄 How It Works:
-----------------
Source Data in Amazon S3
⬇️
Athena Reads Source Data
⬇️
Athena Generates New Output Files
⬇️
EXTERNAL_LOCATION
⬇️
New Files Written to Amazon S3
⬇️
Metadata Created in AWS Glue Catalog
⬇️
New Table Available

📌 Key Points:
---------------
🔸 EXTERNAL_LOCATION specifies where Athena writes new files.
🔸 Athena creates the output dataset in the specified S3 folder.
🔸 The target folder should be empty before execution.
🔸 Reusing a non-empty location may result in: 🚫 HIVE_PATH_ALREADY_EXISTS
🔸 Different table names can still fail if they use the same EXTERNAL_LOCATION.
🔸 Each CTAS operation should use a unique target folder.
🔸 EXTERNAL_LOCATION is a write target where Athena generates new output files.

📘 CSV vs JSON vs Parquet
=========================================================================================================
Feature                          | CSV                          | JSON                         | Parquet
---------------------------------|------------------------------|------------------------------|----------------------------
Data Format                      | Delimited Text               | Semi-Structured Text         | Binary Columnar
Human Readable                   | Yes                          | Yes                          | No
Self-Describing                  | No                           | Partially                    | Yes
Stores Schema Information        | No                           | No                           | Yes
Requires SerDe                   | No                           | Yes (JSON SerDe)             | No
Compression Support              | Limited                      | Limited                      | Yes
Storage Efficiency               | Low                          | Medium                       | High
Query Performance                | Lower                        | Lower                        | Higher
Columnar Storage                 | No                           | No                           | Yes
Metadata Stored in File          | No                           | No                           | Yes
Analytics Friendly               | No                           | Limited                      | Yes
Athena Support                   | Yes                          | Yes                          | Yes
Data Scan Cost                   | Higher                       | Higher                       | Lower
Typical Use Case                 | Data Exchange                | APIs & Log Data              | Data Lakes & Analytics
File Size                        | Larger                       | Larger                       | Smaller
Preferred for Athena Analytics   | No                           | No                           | Yes
=========================================================================================================

💡 Key Learning
🔸 CSV stores data as plain text and depends entirely on Athena table definitions.
🔸 JSON stores data in key-value format and is suitable for semi-structured data.
🔸 Parquet is a self-describing columnar format that stores schema and metadata within the file itself.
🔸 CSV and JSON are human-readable, whereas Parquet is a binary format and cannot be directly read using a text editor.
🔸 Parquet files generally consume less storage space and provide better query performance than CSV and JSON.
🔸 CSV and JSON are commonly used for data exchange and ingestion, while Parquet is commonly used for analytics and data lake workloads.
🔸 For Athena analytics workloads, Parquet is the preferred format because it supports compression, reduces data scans, and lowers query costs.

⭐ Key Learnings and Takeaways:
==================================
🔸 Athena is a serverless query engine that queries data directly from Amazon S3.
🔸 Athena stores table metadata in the AWS Glue Data Catalog, while the actual data remains in Amazon S3.
🔸 Athena never stores table data internally.
🔸 CREATE EXTERNAL TABLE is used when data files already exist in Amazon S3 and only metadata needs to be created.
🔸 CTAS (CREATE TABLE AS SELECT) is used when Athena needs to generate a new dataset and create new output files.
🔸 LOCATION identifies the Amazon S3 folder containing existing data files.
🔸 EXTERNAL_LOCATION identifies the Amazon S3 folder where Athena should write new output files.
🔸 LOCATION is a read path, whereas EXTERNAL_LOCATION is a write path.
🔸 CREATE EXTERNAL TABLE does not create data files; it only creates metadata.
🔸 CTAS creates both metadata and new output files.
🔸 CSV is not a self-describing format and depends on Athena table definitions for schema information.
🔸 JSON is a semi-structured format and requires a JSON SerDe for parsing.
🔸 Parquet is a self-describing, columnar file format that stores schema and metadata within the file itself.
🔸 Parquet files are not human-readable because they are stored in a binary format.
🔸 Athena validates the actual file format and structure, not just the file extension.
🔸 Renaming a CSV file to .parquet does not create a valid Parquet file.
🔸 AWS Glue Crawlers can be used to automatically discover schemas and create metadata for data stored in Amazon S3.
🔸 CTAS is commonly used for CSV → Parquet conversion, JSON → Parquet conversion, data filtering, aggregation, and analytics optimization.
🔸 For Athena analytics workloads, Parquet is generally preferred over CSV because it provides compression, schema information, reduced data scans, and improved query performance.
🔸 Data resides in Amazon S3, metadata resides in AWS Glue Data Catalog, and Athena acts as the Query engine.
